# План

## Шаги

1. **Закрыть критические неизвестные** — проверить реальные ветки V13/V14, риск `latest`, premium-модель, Clipboard API, статический хостинг, безопасность валидатора и брендовые ограничения. Готово = S-01…S-07 имеют ответы и последствия в `spikes/FINDINGS.md`.
2. **Зафиксировать контракты и дизайн-систему** — описать типы каталога, правила статусов и ошибок, интерфейс валидатора, структуру статического приложения; с помощью `ui-ux-pro-max` сохранить визуальные и UX-правила в `design-system/MASTER.md`. Готово = контракты позволяют написать заглушки без уточнений, дизайн покрывает каталог, фильтры, карточки, предупреждения и адаптивность.
3. **Собрать вертикальный срез** — реализовать переключатель V13/V14, три проверенных модуля, карточки, одиночное копирование, уведомление, мобильную компоновку и одну автоматическую проверку manifest. Готово = AC-1, AC-3, AC-4, AC-5 и AC-6 выполняются на локальной сборке.
4. **Довести MVP** — добавить поиск, фильтры, зависимости, состояния, инструкцию, безопасные внешние ссылки, остальные утверждённые данные и CI. Готово = AC-2, AC-7 и AC-8 выполняются, все запланированные задачи стадии 6 закрыты.
5. **Провести независимый и браузерный аудит** — отдельный аудитор проверяет acceptance criteria, затем в одном браузерном экране проверяются основные страницы, мобильный вид, клавиатура, фильтры, копирование и экспорт только если он останется в утверждённом скоупе. Готово = AC-9 выполняется, находки отражены в `audit.md`, `brief.md`, `decisions.md` и задачах.
6. **Подготовить и выполнить релиз** — после явного запуска требуемых предрелизных аудитов закрыть все P1, опубликовать через Sites и проверить основной сценарий на HTTPS-проде. Готово = AC-10 выполняется и `release.md` содержит URL, проверку и способ отката.

## Acceptance criteria

### AC-1 — Версия Foundry и корректная ветка

Дано — каталог содержит одну карточку с разными `tracks` для Foundry VTT 13 и 14 и ещё две реальные проверенные карточки.

Когда — пользователь переключает V13 на V14 и обратно.

Тогда — каждая карточка показывает не более одной ветки выбранной major-версии; manifest URL, версия модуля, compatibility и дата проверки относятся к этой ветке; неподходящая ветка не попадает в DOM как доступная для копирования.

### AC-2 — Поиск и фильтры

Дано — каталог с модулями разных категорий, лицензий, систем и статусов.

Когда — пользователь вводит запрос и последовательно меняет категорию, «бесплатные/премиальные», систему и «только проверенные».

Тогда — видны только записи, удовлетворяющие всем активным условиям; число результатов обновляется; при пустой выдаче показано понятное состояние со сбросом фильтров.

### AC-3 — Копирование ровно одной ссылки

Дано — карточка с проверенным HTTPS manifest URL.

Когда — пользователь нажимает «Скопировать manifest».

Тогда — Clipboard API получает точное значение только этой ветки, появляется сообщение «Manifest-ссылка скопирована», а ни одна другая ссылка не копируется; при отказе Clipboard API URL остаётся видимым и его можно выделить вручную.

### AC-4 — Автоматическая проверка manifest

Дано — три manifest URL вертикального среза.

Когда — выполняется `npm run validate:data`.

Тогда — команда проверяет HTTPS, допустимый конечный адрес, HTTP-ответ, Content-Type/JSON, размер, редиректы, `id`, `title`, `version`, compatibility, `manifest`, `download`, `relationships.requires` и связь с выбранной major-версией; успех завершается кодом 0, намеренно испорченная fixture — ненулевым кодом и конкретной ошибкой.

### AC-5 — Адаптивность и клавиатура

Дано — локальная production-сборка.

Когда — браузерная проверка проходит ширины 375, 768, 1024 и 1440 px, масштаб 200%, последовательный Tab/Shift+Tab и активацию Enter/Space.

Тогда — горизонтального скролла нет, длинные URL и badges не обрезают содержимое, focus state заметен, управление доступно с клавиатуры, а интерактивные элементы имеют понятные accessible names.

### AC-6 — Полностью статическая архитектура

Дано — чистая рабочая копия без секретов и серверных процессов.

Когда — выполняются установка зависимостей по lockfile и `npm run build`, а затем открывается собранный сайт.

Тогда — сборка создаёт статические файлы, поиск/фильтры/копирование работают в браузере, а приложение не принимает пользовательские URL и не требует API, БД или секретов во время выполнения.

### AC-7 — Целостность публичных данных

Дано — полная MVP-выборка каталога.

Когда — выполняются тесты схемы и валидатор.

Тогда — нет дублированных карточек ради разных major-версий; публичные manifest имеют только HTTPS; персональные premium URL и токены отсутствуют; непроверенные записи не входят в выдачу «только проверенные»; каждая проверенная ветка имеет дату и первичные источники.

### AC-8 — Понятное назначение и безопасные ссылки

Дано — главная страница каталога.

Когда — пользователь читает первый экран и открывает карточку.

Тогда — сайт называет себя каталогом/справочником, не установщиком; содержит заметную фразу о неофициальном проекте; кнопка не называется «Скачать модуль»; внешние ссылки открываются с безопасным `rel`; инструкция описывает ручную установку в пяти шагах.

### AC-9 — Автоматический и ручной аудит

Дано — production-сборка и команды запуска из `brief.md`.

Когда — отдельный аудитор запускает тесты, а браузерная проверка проходит версии, поиск, все фильтры, копирование, пустое состояние, мобильный режим и клавиатуру в одном открытом экране.

Тогда — результаты записаны в `docs/pipeline/audit.md`; у каждого AC есть статус и способ проверки; незакрытых критичных дефектов нет.

### AC-10 — Публичный HTTPS-релиз

Дано — явные отчёты `$launch-security` и `$launch-web` без открытых P1.

Когда — сайт публикуется через Sites и основной сценарий повторяется на production URL.

Тогда — URL доступен по HTTPS, V13/V14 переключаются, manifest одной карточки копируется, статические ресурсы загружаются без ошибок, а `docs/pipeline/release.md` фиксирует адрес, версию/коммит, проверку и откат.

## Non-goals

- Автоматическая, массовая или пакетная установка модулей.
- Корзина, очередь, выбранная сборка, «скопировать все» и переход к следующему модулю.
- Экспорт сборки или общий meta-manifest в MVP.
- Отметки «установлено», отслеживание установки и активация в мире.
- Собственный Foundry-модуль, зеркала ZIP и персональные premium manifest URL.
- Пользовательские аккаунты, облачная синхронизация, база данных и серверный API.
- Загрузка manifest URL, введённого посетителем.
- Полное наполнение каталога до утверждения вертикального среза.

## Открытые вопросы

- Сохранять ли рабочее имя `Foundry Loadout` для публичного релиза → риск-спайк S-07 по официальному branding guide; без безопасного решения релиз блокируется.
- Какие три модуля дают честные отдельные ветки V13/V14 → риск-спайки S-01 и S-02, только по официальным manifest, релизам и каталогу.
- Какой минимальный статический UI-стек лучше поддерживает Sites и тестирование → решение на стадии контрактов после S-05.
- 21st.dev MCP недоступен → принятое ограничение; дизайн и компоненты создаются средствами установленного `ui-ux-pro-max` и выбранного стека.
